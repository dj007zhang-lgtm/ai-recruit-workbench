# 硬门槛判定规则

> 硬门槛是一票否决项。不通过就直接淘汰，不进 BARS 判档。
>
> 但「不通过」和「没写」是两件事，必须区分。

## 三态判定

| 状态 | 判定依据 | 后续处理 |
|---|---|---|
| ✅ **通过** | 简历明确写明了满足 | 继续下一项 |
| ❌ **不通过** | 简历明确写明了不满足，**或证据矛盾** | 直接淘汰，不烧后续评估 |
| ⚠️ **待核** | 简历没提这件事，看不出会不会 | 继续，但标记需核实 |

## 核心区分：缺证据 vs 证据矛盾

这是最容易搞错的地方。

### 缺证据 → 待核

**定义**：简历没写这件事。

**例子**：
- 简历通篇没提学历 → 「学历：待核」
- 简历没写英语水平 → 「英语：待核」

**处理**：标「待核」，留给人核实。**不要判不通过**，因为「没写」不等于「没有」。

### 证据矛盾 → 不通过

**定义**：简历里看到了**相反的证据**。

**例子**：
- 技能栏写「熟练掌握 Java 后端」，项目经历全是 Python + Flask
- 简历写「5 年 Java 经验」，但所有项目时间是 2023-2024（只有 1 年）
- 写「统招本科」，但教育经历写「专升本」

**处理**：直接判不通过。因为这不是「信息不足」，是「看到了矛盾」。

### 判定规则

> **项目经历是硬证据，技能自述是软证据。两者冲突时，以项目经历为准。**

为什么？因为技能栏可以随便写，项目经历编不了。

## 技术栈判定细则

### 必须有语言级关键词

判断技术栈是否对口，不能只看通用中间件。

**错误做法**：
```
简历出现 Kafka、MySQL → 认为有 Java 后端经验
```
问题：Python 项目一样用 Kafka 和 MySQL。

**正确做法**：
```
必须有 Java/Spring/MyBatis 这类语言级关键词
通用中间件（Kafka/MySQL/Redis）不算证据
```

### 跨栈错配的处理

| 情况 | 判定 |
|---|---|
| 岗位要 Java，简历全是 Python | ❌ 不通过（明确错配） |
| 岗位要 Java，简历有 Java 也有 Python | ✅ 通过（主栈对口） |
| 岗位要 Java，简历只写「熟悉后端开发」 | ⚠️ 待核（看不出语言） |

## 学历判定细则

### 中文简历

| 表述 | 判定 |
|---|---|
| 「2018-2022 就读于XX大学软件工程」 | ✅ 全日制本科 |
| 「四年制本科」「统招本科」 | ✅ 明确 |
| 「专升本」「自考」「函授」「成人教育」「网络教育」 | ❌ 非统招 |
| 只写「本科」，没写是否统招 | ⚠️ 待核（需核实） |

### 英文简历等价识别

海外/外企简历用英文表述，**必须等价理解**，不得因语言不同判「缺证据」。

| 中文概念 | 英文等价表述 |
|---|---|
| 本科 | Bachelor / B.S. / BSc / BS |
| 硕士 | Master / M.S. / MSc |
| 博士 | Ph.D. / PhD / Doctorate |
| 专科 | Associate degree |
| 四年制本科 | 4-year program / four-year undergraduate |
| 工学学士 | B.Eng / B.Tech |
| 计算机相关专业 | Computer Science / CS / Software Engineering / IT / EECS |
| 全日制 | Full-time / On-campus / Regular program |
| 非全日制 | Part-time / Online / Distance learning / Open University |
| 名校 | QS/THE/US News 排名前列，或国内 985/211/双一流 |

### 毕业时间常识

**以下都是正常现象，不得判疑点**：

- 国内本科 6-7 月毕业
- 国内硕士 3-4 月毕业
- 海外毕业时间各异（常见 5 月、6 月、12 月）

## 年限判定细则

### 怎么算年限

从第一段全职工作经历算起，**不含实习**。

- 毕业前半年到一年在同公司实习后转正 → 从转正起算
- 多段经历有重叠 → 按时间跨度算，不累加

### 什么算断档

| 断档时长 | 判定 |
|---|---|
| ≤2 个月 | 正常（当月离职、次月入职是常态） |
| 2-3 个月 | 可接受，不必追问 |
| ≥3 个月且无合理解释 | 可列为疑点，但**不作为淘汰理由** |

**注意**：即使断档较长，也只能「列为疑点」，不能因此判不通过。这是公平性铁律。

## 输出格式

每条硬门槛这样输出：

```
硬门槛：统招本科
判定：✅ 通过
依据：教育经历写明「2019.09-2023.06 郑州升达经贸管理学院 计算机科学与技术 本科 统招」，
      明确四年制本科且标注统招，未出现专升本/自考/函授等非统招信息。
```

```
硬门槛：核心技术栈 Java
判定：❌ 不通过
依据：技能栏写「熟练掌握 Java 后端开发」，但项目经历中后端实现均写的是
      Python + Flask（「使用 Flask 搭建订单服务」「Django 开发后台管理」），
      未看到任何 Spring/MyBatis 项目证据。技能自述与项目事实矛盾，
      以项目经历为准，判技术栈不匹配。
```

```
硬门槛：英语水平
判定：⚠️ 待核
依据：简历未提及英语水平或任何英语相关证书，看不出是否满足要求，建议面试或电话核实。
```

## 必须先分类：这是硬门槛还是优先条件？

**这是最容易出错的地方，也是真实踩过的坑。**

很多 JD 把「硕士优先」「有大厂经验优先」「英语六级优先」和真正的硬门槛写在一起，
如果全部当硬门槛处理，会导致**合格的人被误杀**。

### 分类规则

| 表述特征 | 归类 | 处理 |
|---|---|---|
| 「必须」「要求」「需具备」「以上学历」 | **硬门槛** | 不满足则淘汰 |
| 「优先」「加分」「最好有」「者优先」 | **优先条件** | 不满足**不影响通过**，只在同等条件下参考 |
| 「熟悉」「了解」「掌握」（技能类） | **软性要求** | 交给 BARS 判档，不淘汰 |
| 「负责」「参与」（职责类） | **岗位职责** | 不是候选人要求，跳过 |

### 识别关键词

**硬门槛信号**：
- 必须、须、要求、需、应具备、限、仅
- 「XX 及以上」「XX 以上」
- 明确年限：「3 年以上」

**优先条件信号**：
- 优先、加分、更佳、最好、优先考虑
- 「者优先」「者更佳」

**软性要求信号**：
- 熟悉、了解、掌握、具备……能力
- 这些**不该**作为一票否决项

### 真实反例

**错误做法**：

```
硬门槛：硕士优先
判定：❌ 不通过（简历只显示本科）
结果：直接淘汰
```

问题：这是**优先条件**，不是硬门槛。候选人本科学历 + 14 年经验完全可能胜任。

**正确做法**：

```
优先条件（非硬门槛）：硕士优先
情况：简历显示本科（浙江大学），无硕士
影响：无。该项为加分项，不影响通过判定。
备注：可在同等条件下作为参考。
```

### 输出时的处理

硬门槛表格只列**真正的硬门槛**。优先条件单独列一小节：

```
## 硬门槛判定

| 门槛 | 判定 | 依据 |
|---|---|---|
| 本科及以上 | ✅ 通过 | 浙江大学本科 |
| 3 年经验 | ✅ 通过 | 2012-2025，14 年 |

## 优先条件（不影响通过判定）

| 条件 | 情况 | 说明 |
|---|---|---|
| 硕士优先 | 未满足（仅本科） | 加分项，不影响判定 |
| 大厂背景 | 满足（阿里巴巴 2 年） | 加分 |
```
