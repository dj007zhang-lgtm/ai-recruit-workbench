# 输出模板

严格按此结构输出。不要增删章节，不要加「总结」「综合来看」这类无信息量的段落。

---

## 标准输出格式

```
# 简历判断：{候选人姓名或「未识别」}

岗位：{岗位名称}
判断时间：{日期}

---

## 一、字段自检

{ok / suspect / poor}

{如有缺失，逐条列出}
- 未识别到 XXX
- 未识别到 XXX

{如为 poor，到此为止，不给后续判断}

---

|---|---|---|
| {门槛1} | ✅ 通过 | {从简历看到什么，所以判定什么} |
| {门槛2} | ❌ 不通过 | {同上} |
| {门槛3} | ⚠️ 待核 | {同上} |

{如有 ❌，到此为止，直接给淘汰结论}

（同上格式）
```

## 简化输出（用户只要快速判断时）

如果用户明确说「简单说一下」「快速看一下」，可以用这个精简版：

```
# {姓名} · {岗位}

**评级**：{S/A/B/C}（{分数} 分）

**硬门槛**：{X/Y 通过}{，有 N 项待核}

**关键依据**：
- {维度1}：L{X} — 「{原文}」
- {维度2}：L{X} — 「{原文}」

**需要核实**：
- {疑点1}
- {疑点2}

**建议**：{一句话}
```

---

## 不要这样写

**❌ 没有原文引用的判档**

```
技能与专业深度：L2
理由：技术能力较强，有丰富项目经验
```

问题：没有原文，「技术能力较强」是感觉不是证据。

**✅ 正确写法**

```
技能与专业深度：L2
证据：「主导分布式微服务架构设计与性能治理：服务拆分、分片方案设计、多级缓存、消息队列、分布式锁」
理由：有架构设计案例（服务拆分、分片方案），覆盖多个技术领域，符合 L2「精通核心栈且有架构案例」。
```

---

**❌ 没有信息量的建议**

```
建议进一步沟通了解情况。
```

**✅ 正确写法**

```
建议：安排技术面，重点验证「高并发」是否真实——简历写「支撑百万 QPS」但未说明具体架构方案，需当面确认。
```

---

**❌ 模糊的档位**

```
技能深度：介于 L1 和 L2 之间
```

**✅ 正确写法**

```
技能深度：L1
理由：有多个技术栈使用记录（Spring、MySQL、Redis），但均为「使用」层面描述，未看到架构设计或复杂问题解决的案例，不满足 L2 的「有架构/性能/复杂问题解决案例」。偏严格判 L1。
```
